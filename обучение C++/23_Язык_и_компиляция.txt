## 1. Фазы трансляции (Translation Phases)

Стандарт C++ (ISO/IEC 14882) определяет **9 фаз трансляции** (C++23: [lex.phases]). Они выполняются последовательно:

### Фаза 1: Маппинг физических символов
- Исходный файл считывается как последовательность бит
- Преобразуется в базовый набор символов (basic source character set)
- Trigraphs заменяются (устарело в C++17, удалено в C++23)
- Universal character names (UCN) `\uXXXX` / `\UXXXXXXXX` распознаются

### Фаза 2: Сшивка строк (Line splicing)
- Обратный слэш `\` в конце строки удаляется вместе с `\n`
- Физические строки объединяются в логические

### Фаза 3: Токенизация (Tokenization)
- Исходник разбивается на препроцессинговые токены:
  - идентификаторы, ключевые слова, литерулы, операторы, пунктуация
- Комментарии заменяются на один пробел
- Директивы препроцессора распознаются

### Фаза 4: Препроцессинг (Preprocessing)
- `#include` — рекурсивное включение файлов (фазы 1–4 повторяются)
- `#define` / `#undef` — макросы
- `#if` / `#ifdef` / `#else` / `#endif` — условная компиляция
- `__LINE__`, `__FILE__`, `__DATE__`, `__TIME__`, `__cplusplus`, `__has_include`, `__has_cpp_attribute`

### Фаза 5: Escape-последовательности в символьных и строковых литерулах
- `\n`, `\t`, `\"`, `\'`, `\\`, `\xNN`, `\uNNNN`, `\UNNNNNNNN` преобразуются

### Фаза 6: Конкатенация строковых литерулов
- Соседние строковые литерулы объединяются: `"Hello" "World"` → `"HelloWorld"`

### Фаза 7: Компиляция (Parsing + Semantic Analysis)
- Препроцессинговые токены → токены C++
- Синтаксический анализ (parsing)
- Семантический анализ: проверка типов, разрешение имен, overload resolution, template instantiation
- Генерация AST

### Фаза 8: Инстанцирование шаблонов (Template Instantiation)
- Неявное инстанцирование при использовании
- Явное инстанцирование: `template class MyClass<int>;`
- Экспорт шаблонов (export — удалён в C++11, модули заменяют)

### Фаза 9: Линковка (Linking)
- Объединение объектных файлов (.obj/.o) в исполняемый модуль
- Разрешение внешних символов (external linkage)
- Устранение неиспользуемых символов (COMDAT folding, ICF)

## 2. ODR — One Definition Rule (Правило одного определения)

### Основное правило ([basic.def.odr])
> В каждой единице трансляции (TU) каждое имя должно иметь **ровно одно определение**. В всей программе — не более одного определения для сущностей с внешним связыванием.

### Что считается определением:
- Функция с телом: `void foo() {}`
- Переменная с инициализатором (не `extern`): `int x = 42;`
- Класс/структура/перечисление: `struct S {};`
- Шаблон: `template <typename T> void f() {}`
- Статический член класса с инициализатором (C++17 inline variables)

### Что НЕ является определением:
- Объявление функции: `void foo();`
- `extern int x;`
- forward declaration класса: `class Foo;`
- Шаблон без тела (forward declaration)

### ODR для inline-функций и переменных (C++17)
```cpp
// header.h
inline int global_counter = 0;           // OK: одно определение во всей программе
inline void log(const char* msg) {       // OK: inline function
    std::cout << msg << '\n';
}

template <typename T>
inline constexpr T pi = T(3.1415926535897932385); // C++17 inline variable template
```

### Нарушения ODR (UB):
```cpp
// file1.cpp
struct S { int a; void f() { std::cout << "file1\n"; } };
void use() { S s; s.f(); }

// file2.cpp
struct S { int b; void f() { std::cout << "file2\n"; } }; // ODR violation!
void use2() { S s; s.f(); }
```
**Последствие**: поведение не определено. Линкер может выбрать любое определение.

### ODR и шаблоны
Шаблоны должны быть **идентичны** во всех TU (token-for-token после препроцессинга, за исключением невидимых различий).

### Инструменты диагностики ODR:
- `-Wodr` (GCC/Clang)
- `/d1reportSingleClassLayout` (MSVC)
- `ldd --verify` / `dumpbin /exports` — проверка символов
- AddressSanitizer: `-fsanitize=odr` (GCC 12+, Clang)

## 3. Linkage (Связывание) и Storage Duration

### Виды связывания ([basic.link])

| Linkage | Ключевые слова | Видимость | Примеры |
|---------|---------------|-----------|---------|
| **External** | (default для функций, переменных в namespace) | Вся программа | `int x; void f();` |
| **Internal** | `static` (в namespace), `constexpr` (C++17), `const` (C++98/03) | Только TU | `static int x; constexpr int Y = 1;` |
| **No linkage** | Локальные переменные, параметры, лямбды без capture | Только блок | `void f() { int x; }` |
| **Module linkage** (C++20) | `export` в модулях | Внутри модуля | `export module M; export int x;` |

### Правила:
```cpp
// namespace scope
int a;              // external linkage
static int b;       // internal linkage
const int c = 1;    // internal linkage (C++98-17), external в C++20 без inline
inline int d = 2;   // external linkage, ODR-safe
constexpr int e = 3; // internal linkage (implicit inline since C++17)
extern const int f; // external linkage (declaration)

thread_local int tls_var; // external linkage, per-thread storage
```

### Storage Duration (Время хранения) ([basic.stc])

| Duration | Ключевые слова | Инициализация | Уничтожение |
|----------|---------------|---------------|-------------|
| **Static** | `static` (namespace), `thread_local`, globals | До `main()` (constant init) / до первого использования (dynamic init) | После `main()` / при выгрузке DLL |
| **Thread** | `thread_local` | При старте потока | При завершении потока |
| **Automatic** | Локальные переменные | При входе в блок | При выходе из блока (деструктор) |
| **Dynamic** | `new` / `malloc` | При вызове `new` | При `delete` / `free` (ручное) |

### Порядок инициализации (Static Initialization Order Fiasco):
```cpp
// a.cpp
#include "b.h"
int a = get_b() + 1; // UB: b может быть неинициализирован

// b.cpp
int b = 42;
int get_b() { return b; }
```
**Решение**: Construct On First Use Idiom / `inline` переменные / модули C++20.

## 4. Lifetime (Время жизни объектов) ([basic.life])

### Начало lifetime:
- Для объектов со static/thread storage duration — после инициализации
- Для automatic — при входе в блок (после инициализации)
- Для dynamic — после завершения конструктора в `new`
- Для subobjects — после инициализации полного объекта

### Конец lifetime:
- Вызов деструктора (явный или неявный)
- `free` / `delete` / переиспользование памяти (`std::launder`)
- Выход из области видимости (automatic)

### Доступ вне lifetime (UB):
```cpp
struct A { int x; ~A() { std::cout << "dtor\n"; } };

void foo() {
    A a;        // lifetime begins
    a.~A();     // lifetime ends
    a.x = 42;   // UB! доступ к мёртвому объекту
}

void bar() {
    alignas(A) char buf[sizeof(A)];
    A* p = new (buf) A(); // placement new
    p->~A();              // explicit dtor call
    // p всё ещё указывает на память, но объект мёртв
    // std::launder(p) — получить указатель на новый объект в той же памяти
}
```

### `std::launder` (C++17) — получение валидного указателя после переиспользования памяти:
```cpp
#include <new>
#include <memory>

struct Node { int value; Node* next; };

void replace(Node* p, int new_val) {
    p->~Node();                    // destroy old
    new (p) Node{new_val, nullptr}; // construct new in same storage
    // p теперь указывает на старую память, но новый объект!
    // Для доступа нужно:
    Node* valid = std::launder(p); // OK
    valid->value = 99;
}
```

## 5. Undefined Behavior (UB) — Классификация и последствия

### Что такое UB ([intro.defs]):
> Поведение, для которого стандарт накладывает **никаких требований**. Программа может: работать "правильно", падать, выдавать неверные результаты, весить себя из памяти, форматировать диск.

### Классификация UB:

| Категория | Примеры |
|-----------|---------|
| **Memory** | Buffer overflow, use-after-free, double-free, dangling pointer, unaligned access |
| **Type** | Strict aliasing violation, type punning через union (до C++20), `reinterpret_cast` abuse |
| **Lifetime** | Access outside lifetime, virtual call in ctor/dtor, `delete` без virtual dtor |
| **Integer** | Signed overflow, shift ≥ width, shift negative, div by zero |
| **Pointer** | Dereference null, pointer arithmetic past one-past-end, compare unrelated pointers |
| **Concurrency** | Data race (не atomic, не mutex), double-checked locking без atomics |
| **Control flow** | Infinite loop без side effects (C++26: `[[assume]]`), `noreturn` возвращает |
| **Library** | Invalid iterator, modifying const via `const_cast`, `std::function` от moved-from |

### UB vs Implementation-Defined vs Unspecified:
| Категория | Описание | Пример |
|-----------|----------|--------|
| **Undefined Behavior** | Никаких гарантий | `int* p = nullptr; *p = 1;` |
| **Implementation-Defined** | Компилятор должен задокументировать | `sizeof(int)`, order of evaluation (mostly) |
| **Unspecified Behavior** | Допустимы варианты, недокументированы | Порядок вычисления аргументов функции (до C++17) |

### Инструменты обнаружения UB:
```bash
# Sanitizers (GCC/Clang)
-fsanitize=address          # ASan: use-after-free, buffer overflow
-fsanitize=undefined        # UBSan: signed overflow, alignment, vptr, etc.
-fsanitize=thread           # TSan: data races
-fsanitize=memory           # MSan: uninitialized reads
-fsanitize=leak             # LSan: memory leaks

# MSVC
/fsanitize=address
/fsanitize=undefined (Preview)
```

### Некоторые "惊人" UB примеры:
```cpp
// 1. Signed overflow
int x = INT_MAX;
x += 1; // UB! (не wrap-around)

// 2. Null dereference в constexpr (C++20)
constexpr int f() { return *nullptr; } // UB даже в constexpr

// 3. Infinite loop без side effects
while (true) { } // UB в C++26 (может быть оптимизирован в nop)

// 4. Type punning через union (до C++20)
union { float f; int i; } u;
u.f = 1.0f;
int bits = u.i; // UB до C++20, OK в C++20 (std::bit_cast предпочтительнее)

// 5. Modify string literal
char* p = "hello";
p[0] = 'H'; // UB

// 6. Virtual call в конструкторе
struct Base { virtual void f() {} Base() { f(); } }; // вызывает Base::f, не Derived::f
struct Derived : Base { void f() override {} };
```

## 6. Работа со стандартом C++

### Структура стандарта (ISO/IEC 14882):
- **Clause 1–3**: Scope, Normative references, Terms
- **Clause 4–16**: Language (lex, basic, expr, stmt, dcl, class, temp, etc.)
- **Clause 17–33**: Library (containers, algorithms, iterators, ranges, threads, etc.)
- **Annex A–B**: Grammar summary, Compatibility

### Номенклатура разделов:
- `[lex.phases]` — фазы трансляции
- `[basic.def.odr]` — ODR
- `[basic.link]` — linkage
- `[basic.life]` — lifetime
- `[intro.defs]` — определения (UB, IDB, unspecified)
- `[expr.add]` — pointer arithmetic
- `[class.cdtor]` — ctor/dtor semantics

### Как читать стандарт:
1. Начните с **cppreference.com** — читаемая версия с примерами
2. Ищите по разделу: `https://eel.is/c++draft/basic.life`
3. Используйте **latest draft** (N4950 для C++23, N4980 для C++26)
4. Комментарии в стандарте — не нормативны, но полезны

### Полезные ресурсы:
- **C++ Standard Draft** — https://eel.is/c++draft/
- **cppreference** — https://en.cppreference.com/
- **C++ Core Guidelines** — https://isocpp.github.io/CppCoreGuidelines/
- **Compiler Explorer** — https://godbolt.org/ (проверка кодогенерации)
- **C++ Insights** — https://cppinsights.io/ (template instantiation, implicit code)

### Задание 4: Lifetime и `std::launder`
Реализуйте пул объектов с placement new и повторным использованием памяти. Используйте `std::launder` для корректного доступа.

### Задание 5: UB Hunt
Найдите UB в коде:
```cpp
int* create_array(int n) {
    int arr[n]; // VLA — не стандартный C++!
    return arr; // возвращает указатель на automatic storage
}

int main() {
    int* p = create_array(10);
    p[0] = 42; // UB!
}
```
Исправьте с использованием `std::vector` или `std::unique_ptr<int[]>`.
